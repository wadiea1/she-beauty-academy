# Production deployment — topology, requirements, and blockers

Status: **not deployed, not launched.** This document is the deployment
contract for SHE Beauty Academy. It records what the application actually
requires, what is already safe, and what a human owner must still decide or
supply before anything goes live.

Nothing here provisions infrastructure, selects a hosting provider, registers
a domain, or creates credentials. Those are deliberate owner decisions and are
listed as blockers below.

---

## 1. Audit of the current state (Milestone M, pre-implementation)

### Application shape

| --- | --- |

| CMS | Payload 3.88.0, mounted inside the same Next app (`src/app/(payload)/`) |
| Database | PostgreSQL via `@payloadcms/db-postgres` 3.88.0 |
| Node / pnpm | Node 24, pnpm 11.22.0 (`packageManager` pinned) |
| Rendering | Every public route is dynamic (`ƒ`); no `generateStaticParams` anywhere |

| Media uploads | Local disk — `media/` at the repo root, gitignored, currently empty |

### Payload 3.88 migration facts (read from installed source)

- `node_modules/payload/dist/bin/migrate.js` — the available commands are
  exactly: `migrate`, `migrate:create`, `migrate:down`, `migrate:refresh`,
  `migrate:reset`, `migrate:status`, `migrate:fresh`.
- `migrate:create` runs with `disableDBConnect: true` — creating a migration
  needs **no** database connection.
- `@payloadcms/drizzle/dist/utilities/buildCreateMigration.js` — a migration is
  generated by diffing the **latest `.json` snapshot in the migrations
  directory** against a snapshot of the **current Payload config schema**. It
  does not read the live database. With an empty migrations directory the
  "before" side is Payload's `defaultDrizzleSnapshot`, so the first generated
  migration is a **complete current-schema baseline** — which is exactly what
  this milestone needs.
- `payload/dist/database/migrations/findMigrationDir.js` — with no
  `migrationDir` configured, the directory resolves to **`src/migrations`**.
- `payload/dist/database/migrations/writeMigrationIndex.js` — it treats
  **every** `.ts`/`.js` file in that directory (except `index`) as a migration
  and re-exports its `up`/`down`.
- `@payloadcms/db-postgres/dist/connect.js` — dev schema push runs only when
  `NODE_ENV !== 'production'` **and** `PAYLOAD_MIGRATING !== 'true'` **and**
  the adapter's `push` option is not `false`. So production already never
  pushes; `push: false` in production is belt-and-braces, not the only guard.
- The same file will **auto-create the database** if it does not exist
  (unless `disableCreateDatabase: true`), and will **drop all tables** if
  `PAYLOAD_DROP_DATABASE=true` is set.
- The adapter also supports `prodMigrations`, which runs migrations
  automatically during `connect()` in production. See §4 for why this project
  deliberately does not use it.

### Real findings that needed fixing in this milestone

1. **`src/migrations/` was already occupied by a non-migration script.**
   `migrate-admin-role.ts` (the one-off Milestone J admin-role promotion, run
   via `payload run`) lived in Payload's default migration directory. It
   exports no `up`/`down`, so `writeMigrationIndex` would have swept it into
   the generated migration index and produced a broken migration set. Moved to
   `src/scripts/` so `src/migrations/` is exclusively Payload's.
2. **No formal migrations existed at all** — development relied entirely on
   dev-mode schema push, which is unavailable in production by design.
3. **Rate limiting is in-memory** — per-process, resets on restart, not shared
   across instances. Not production-grade for a public form.
4. **Privacy policy version is `unpublished-v0`** and there is no approved
   policy content, yet the public lead form collects real PII.
5. **Media is local disk** — lost on any ephemeral/replaced filesystem.
6. **No health/readiness endpoint**, **no security headers**, and
   **`next.config.ts` was empty**.
7. **CI ran lint + build only** — no typecheck step, no migration verification.
8. **README was still the unmodified `create-next-app` template.**
9. **The admin session cookie had no `Secure` flag.** `auth: true` on the
   Users collection takes Payload's cookie defaults, and those are
   `sameSite: 'Lax'`, `secure: false`
   (`payload/dist/collections/config/defaults.js`). Confirmed live against a
   production build: `Set-Cookie: payload-token=…; Path=/; HttpOnly=true;
   SameSite=Lax` — no `Secure`. Fixed in `src/collections/Users.ts` by
   setting it from the configured origin rather than `NODE_ENV`, so a real
   https deployment gets the flag while `pnpm start` against
   `http://localhost` still works for production-mode testing. Re-verified:
   with an https origin the cookie now carries `Secure=true`.

### Session and cookie review (Payload 3.88)

Defaults read from installed source and deliberately left as-is:

| Setting | Value | Assessment |
| --- | --- | --- |
| `sameSite` | `Lax` | Correct for an admin panel — the cookie still survives top-level navigation into `/admin` while not being sent on cross-site subrequests. `Strict` would break returning to the panel from an external link for no real gain. |
| `httpOnly` | `true` | Not readable from JavaScript. |
| `secure` | now origin-derived | See finding 9. |
| `tokenExpiration` | 7200s (2h) | Reasonable for staff. Shortening it mainly logs editors out mid-edit. |
| `maxLoginAttempts` | 5 | Account lockout is on by default. |
| `lockTime` | 600000ms (10min) | Reasonable. |

### Graceful shutdown

Next registers `SIGINT`/`SIGTERM` handlers in
`next/dist/server/lib/start-server.js`, closes the HTTP server, and exits
`143`/`130`. Neither Payload nor the Postgres adapter registers signal
handlers, so the connection pool is torn down by process exit rather than
drained. Acceptable here: requests are short and read-mostly, and the
server stops accepting new connections first. **No custom server was
added** — replacing `next start` to drain a pool would be a larger
correctness risk than the one it removes.

### Docker

**Not added.** The Docker CLI is installed on this machine but its daemon
is not running, so a Dockerfile could not be built or run even once. Per
the brief, an untested container definition is worse than none — it looks
authoritative while nobody has ever executed it. The application is a
standard `pnpm install && pnpm build && pnpm start` Node 24 service; the
capability table in §2 is what a container or buildpack has to satisfy.

## 2. Production topology — capabilities required

**No hosting provider has been selected, and this repository is deliberately
not optimized for any specific one.** The application is a standard
long-running Node server; the list below is what a candidate platform must be
able to provide.

| # | Capability | Why | Notes |
| --- | --- | --- | --- |
| 1 | Long-running Node 24 process | Next.js server + Payload Admin + API in one app | `pnpm build` then `pnpm start`. A short-lived/serverless-only model would need the in-process rate limiter replaced first (§6) and complicates DB connection pooling. |
| 2 | Managed PostgreSQL | All CMS content, users, and leads | Must allow TLS connections and enough concurrent connections for the app pool + migration runs. |
| 3 | Automated database backups + restore | Leads and CMS content are irreplaceable | Must be **verified**, not assumed — see the runbook. |
| 4 | Persistent object/media storage | Payload Media currently writes to local disk | Required before anyone uploads real photography. See §7. |
| 5 | Environment secret storage | `PAYLOAD_SECRET`, `DATABASE_URI` | Must never be committed or logged. |
| 6 | HTTPS with a real certificate | Auth cookies, SEO canonicals, general integrity | Payload's admin session cookie expects a secure context in production. |
| 7 | Shared/durable rate-limit backend | Public form abuse protection across instances/restarts | See §6 — currently a launch blocker, not a solved problem. |
| 8 | Log aggregation | Operational visibility without PII leakage | See the logging expectations in the runbook. |
| 9 | A way to run one-off commands | `pnpm payload:migrate`, `pnpm seed` | Needed for deployment and content bootstrap. |

Deployment shapes compatible with the above include a container/VM platform, a
managed Node application platform, or a self-managed VM behind a reverse
proxy — **none of which has been chosen**. Nothing in the repository assumes
any of them.

## 3. Launch blockers (owner/legal/provider decisions)

These are **not** engineering tasks that were skipped. Each requires
information or a decision only the business owner can supply. The software has
been made to fail *safely* around each one.

| Blocker | Current state | What is needed |
| --- | --- | --- |
| **Hosting provider + PostgreSQL** | None chosen | Owner selects a platform meeting §2 |
| **Production domain** | None. `NEXT_PUBLIC_SERVER_URL` is `http://localhost:3000` locally | A real domain + HTTPS; set the variable to it |
| **`PAYLOAD_SECRET`** | Local/CI values are obvious non-secrets | Operator generates a strong secret at deploy time (never committed — see the runbook for the command) |
| **Privacy policy** | `PRIVACY_POLICY_VERSION = 'unpublished-v0'`; no policy content exists | Real, legally-reviewed policy text + an approved version identifier. **Not AI-generated.** |
| **Public lead intake** | Fail-closed in production until the two conditions above are met | Approved privacy policy + a durable rate limiter |
| **Durable rate limiting** | In-memory only | A shared store, or acceptance of single-instance operation (see §6) |
| **Media storage** | Local disk | A persistent object-storage provider before real uploads |
| **Database backups** | None (no database provisioned) | Automated backups + a *tested* restore |
| **Search indexing** | `ALLOW_SEARCH_INDEXING` unset → crawlers disallowed everywhere | Turned on **last**, only after everything above is done |

## 4. Migration strategy

Formal, committed migrations replace dev-mode schema push for any environment
that is not local development.

- Migrations live in `src/migrations/` and **are committed to git**.
- `pnpm payload:migrate` applies pending migrations; `pnpm payload:migrate:status`
  reports what is applied; `pnpm payload:migrate:create` generates a new one
  after a schema change.
- **Migrations are run as a deliberate deployment step, never automatically on
  app boot.** Payload's `prodMigrations` adapter option would run them inside
  `connect()`, which means every replica racing the same migration on startup
  and a schema change hiding inside an ordinary restart. This project runs them
  explicitly instead, before the new application version starts serving.
- `migrate:fresh`, `migrate:reset`, and `migrate:refresh` are **destructive**
  and are deliberately not wired to any `pnpm` script. `PAYLOAD_DROP_DATABASE`
  must never be set in production.

### The existing dev database is a special case

`pnpm payload:migrate:status` against the local `she_academy` reports the
baseline as **`Ran: No`**, and that is expected, not a fault. That database
was built entirely by dev-mode schema push before formal migrations existed,
so its tables are already present while the `payload_migrations` ledger is
empty. Running `pnpm payload:migrate` against it would try to `CREATE TABLE`
things that exist and fail.

This matters only for that one pre-existing database. Any **fresh** database
— which is what production will be — takes the baseline cleanly; that was
proved twice this milestone, against a disposable `she_academy_migration_test`
locally and against the CI job's throwaway Postgres, both from empty, and in
both cases Payload then initialized and queried every collection and global
under `NODE_ENV=production` (schema push disabled).

If the local dev database ever needs to be brought under migration control,
the safe route is to recreate it from empty and run `pnpm payload:migrate`,
not to force the baseline onto the existing schema.

See `docs/RUNBOOK.md` for the ordered deployment procedure and the rollback
model.

## 7. Media storage

`Media` uploads write to `media/` on the application's local disk
(`src/collections/Media.ts`, `staticDir`). On any platform with an ephemeral or
replaced filesystem — containers, most managed Node platforms — **uploaded
files are lost on redeploy or restart**, while the corresponding Payload
`media` rows survive in Postgres. That mismatch produces broken image
references that a database restore alone cannot repair.

No storage provider has been configured, because none has been approved. Before
anyone uploads real photography, the owner must choose an object-storage
provider and the corresponding Payload storage adapter must be added. Until
then, treat uploads as **local-development only**.

Backups therefore have two independent halves:

1. **PostgreSQL** — content, users, leads, and media *metadata*.
2. **Object storage** — the uploaded file bytes themselves.

Restoring one without the other leaves the site inconsistent.
